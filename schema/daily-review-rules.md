# 每日复盘与日程转化规则

## 目标

每日复盘不仅保存经验，也要把真正值得执行的建议转化为 Obsidian 工作台可见的日程；同时避免 AI 未经确认就替用户制造任务、决定日期或增加待办压力。

因此，完整流程必须分成两个彼此独立的阶段：

1. **复盘阶段**：恢复长期上下文、核对事实、完成复盘并保存。
2. **日程阶段**：提出少量候选任务，获得用户明确确认后才写入工作台。

完成复盘不等于获得日程写入授权。

## 第一阶段：完成复盘

1. 按长期记忆检索规则读取人物页、总索引、最近三份日志和相关页面。
2. 区分用户亲自完成、Agent／自动化产物、尚未完成、待验证假设和未来想法。
3. 先在对话中帮助用户澄清事实、收获、教训和边界。
4. 用户要求落盘后，保存到 `inbox/dailyreview/YYYY-MM/YYYY-MM-DD.md`，并在当日日志登记。
5. 复盘正文可以记录“尚未完成”和“后续方向”，但这些内容此时仍不是工作台任务。

## 第二阶段：提出候选日程

复盘完成后，从以下内容中筛选候选任务：

- 已经影响客户承诺、收入、交付或明确截止时间的未完成事项；
- 能验证当日关键假设的最小行动；
- 用户明确表示“明天／接下来要做”的事项；
- 不执行就很可能遗忘、并且确实值得进入当前主线的建议。

不要把下列内容直接转成候选任务：

- 每一条泛化建议；
- 纯粹的感想、可能性或未经验证的产品构想；
- Agent 已经自动完成的动作；
- 客户、合作方或其他人需要完成的学习、回复、决策或行为；这些不是用户本人的日程任务；
- 没有明确完成标准的“继续研究”“持续优化”“多学习”；
- 已存在于 `inbox/tasks/` 的重复任务；
- 与当前主线关系弱、只会扩大待办堆积的探索。

### 任务所有权门禁

候选任务必须是用户本人能够直接采取并完成的行动。生成候选前必须回答：

1. 这件事的实际执行者是谁？
2. 用户能否在不依赖他人行为的情况下判断自己已经完成？
3. 完成标准衡量的是用户交付的产物，还是试图控制客户的学习结果？

如果预期结果发生在别人身上，应改写为用户可控的准备、交付、跟进或验证动作。例如：

- 错误：`让段思远独立完成一个 Codex 任务`——执行者和结果主体是段思远。
- 正确：`为段思远第二节课完成备课材料`——执行者是用户，产物可以直接验收。
- 如果确实需要验证客户学习效果，应写成：`设计并实施 Codex 实操题，记录段思远的完成情况与卡点`，但只有用户确认该验证属于自己的工作安排后才能加入日程。

默认只提 **1—3 个**高价值候选，除非用户明确要求完整拆解。每项必须包含：

| 字段 | 要求 |
|---|---|
| 编号 | 用于逐项确认 |
| 所有者 | 默认必须是用户本人；其他人的行为不得进入用户日程 |
| 任务 | 以可执行动词开头，范围足够小 |
| 完成标准 | 只衡量用户可控的产物或动作，能判断“做完／没做完” |
| 建议日期 | 明确到 `YYYY-MM-DD`；只是建议，不是决定 |
| 优先级 | ⏫ 高 / 🔼 中 / 🔽 低 |
| 目标计划 | 默认建议当前月份的 active 计划文件 |
| 来源 | 链接当日复盘 |

## 强制确认门禁

在写入 `inbox/tasks/` 前，必须把候选表展示给用户并请求确认。

以下回复才算明确授权：

- “全部确认”；
- “加入 1、3”；
- “第 2 项改到 8 月 25 日后加入”；
- 其他能唯一确定任务、日期、优先级和目标计划的明确指令。

以下情况不算授权：

- 用户没有回复；
- “可以考虑”“以后再说”“看起来不错”等模糊表达；
- 用户只确认复盘内容正确；
- 用户只说“落盘”，但没有确认候选任务。

没有明确授权时，候选任务只停留在对话中，不得进入工作台。

## 确认后的写入规则

1. 写入前检索 `inbox/tasks/`，按任务核心动作、目标对象和复盘来源查重。
2. 优先写入当前月份已有的 `type: plan`、`status: active` 文件；如果目标计划不明确或不存在，先询问，不擅自创建。
3. 工作台识别的任务格式为：

```markdown
- [ ] 可执行任务 → [[inbox/dailyreview/YYYY-MM/YYYY-MM-DD|来源复盘]] 📅 YYYY-MM-DD 🔼
```

4. `📅` 表示截止日期；`⏫`、`🔼`、`🔽` 分别表示高、中、低优先级。元数据必须放在任务行尾。
5. 高优先级只用于客户承诺、收入阻塞、明确截止日期或关键依赖；一般推进事项默认中优先级；探索性任务默认低优先级。
6. 写入后验证目标文件仍为 `type: plan`、`status: active`，任务语法能够被 Knowledge Workbench 解析。
7. 在当日复盘追加“已转化为日程”记录，列出写入的计划文件、任务、日期和优先级。
8. 在当日日志记录日程转化；如果用户拒绝或暂缓，不创建任务，也不把候选伪装成已安排事项。

## 防止日程膨胀

- 同一持续性习惯不应每天生成重复任务；优先维护一个现有任务或单独设计周期机制。
- 不替客户、合作方或 Agent 建立任务，也不把他人的预期结果伪装成用户待办。
- 任务必须服务于求职转型、能力深化、商业经营、内容与社群四条主线之一，或服务于明确的生活承诺。
- 当候选超过 3 项时，先排序并说明取舍，不把复盘变成新的任务债务。
- 如果建议仍需先做选择，候选任务应是“完成决策／验证”，而不是直接执行尚未确认的方案。
